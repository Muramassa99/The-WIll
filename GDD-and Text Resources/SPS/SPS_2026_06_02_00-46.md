### Material Intersection And Material Cost

The user clarified same-material behavior.

Target behavior:

- If two same-material strokes overlap or cross, the material should merge into one continuous same-material body.
- The overlap area should not count as double-density material.
- Material cost should count occupied material volume, not repeated drawing over already-occupied same-material volume.
- Same material should behave like one material structure, not stacked independent density.

Different material behavior:

- Replacement should not be treated as a vague "put B over A" stack.
- Replacement should behave as a sequence:
  1. remove/erase the old material in the affected stroke volume;
  2. then place the new material into that resulting air/empty space.
- That gives replacement the visual result of replacing A with B while keeping the conceptual solve cleaner.

Empty-only behavior:

- If the mode is air/empty-only or non-destructive addition, the pass should not interfere with existing material.
- It should only deposit where legal empty space exists.

Important warning:

- Earlier self-checking/intersection solving could hang the system when a single spline/body crossed itself many times.
- Avoid any future same-body self-intersection solve that scans or rebuilds too aggressively without bounds.
- If self-intersection support is improved later, keep it bounded to the affected zone and run it as a short release-time solve, not as an uncontrolled hot-path rebuild.

## New Current State

Forge V2 is no longer just a 2D/grid-inspired material placement experiment. The current design state is:

- Author in 3D.
- Use CSG as the editing/creation workflow.
- Use spline/path tools for controlled material placement.
- Keep finished material targetable.
- Treat finished strokes as real authored material quickly enough for constructive layering.
- Save Forge V2 work through project-compatible WIP systems.
- Move handle validity from inferred geometry/material checks into explicitly authored semantic handle sections.

The most important architectural shift:

- Stage 1 V1 detected valid handles by looking at material, grid slices, profile masks, drift, and clearance.
- Forge V2 should create valid handles through a dedicated authoring mode.
- That changes handle validity from "the system guesses whether generic material looks like a handle" to "the user used the Handle tool to create a handle with an approved profile and valid metric length."

This is not just UI polish. It changes the data contract:

- A Forge V2 handle should carry semantic identity.
- It should know it is a handle because it was authored as a handle.
- Its material can be any selectable construction material.
- Its profile should come from the known Stage 1 handle profile definitions.
- Its path should come from a three-point spline.
- Its length should be checked in meters using Stage 1's voxel-to-meter scale.

## Detailed Explanation

### Why The Old Stage 1 Handle Logic Does Not Directly Fit Forge V2

Stage 1 V1 is grid-based. It can look at voxel/cell occupancy and ask questions like:

- Is this region made of a material that is allowed to be an anchor/grip?
- Does this slice match one of the approved handle footprint profiles?
- Does the handle keep enough empty space around the slice?
- Does the slice drift too much as it moves along its axis?
- Is the valid span long enough?

That makes sense in Stage 1 V1 because the user is depositing on a grid and the shape is inspected after the fact. The system infers meaning from the final occupied cells.

Forge V2 is different:

- It is CSG-based.
- It is metric, not cell-first.
- It can have smooth 3D paths.
- It can use materials that were not valid Stage 1 handle materials.
- It can place geometry in ways that do not map cleanly to old per-slice drift checks.

Because of that, the old question "does this generic placed matter look like a handle?" becomes the wrong question for Forge V2.

The Forge V2 question should be:

- Did the user create this section with the Handle tool?
- Did the user choose a valid handle profile?
- Is the resulting handle path long enough in meters?

That is cleaner and more reliable because the user's authoring intent becomes data.

### Handle Material Rule Change

Old Stage 1 V1 restriction:

- Handle/grip validity depended partly on material type.
- The system could ask whether the material was allowed to be an anchor/grip material.

Forge V2 decision:

- Material type should not decide whether a Forge V2 handle is a valid handle.
- The user can make a handle from any selectable construction material.
- Bone, iron, wood, or other construction materials can all be valid if placed through the Handle tool.

Reason:

- Forge V2 has a dedicated authoring path for handles.
- The handle identity comes from the tool and profile, not from material category.
- This gives more player/build freedom while keeping the data semantically clear.

Important caution:

- This does not mean every random piece of material is a handle.
- It means any construction material can be used by the dedicated Handle tool to create a handle.

### Handle Shape/Profile Rule

The user wants a third option under:

```text
Shape -> Tool -> Handles
```

The Handles option should open a Stage 1 style visual profile picker.

The profile source should be the existing Stage 1 handle profile library:

- Use the same approved handle profile masks/rows.
- Use the same kind of visual representation for selection.
- Do not invent a new unrelated handle profile set unless the user asks.

Important distinction:

- The picker image/icon is UI.
- The real source of truth is the profile definition data.
- The CSG generation should use profile data, not a screenshot or image trick.

Initial handle behavior:

- Select a handle profile.
- Place exactly the required three spline points for the handle path.
- Generate a continuous CSG handle section swept along that 3-point spline.
- The selected profile becomes the cross-section of the swept handle.

### Why Three Points

The user wants handles to be flexible but controlled.

Three points are enough because:

- A straight handle is easy: the middle point can stay aligned.
- A slightly curved handle is possible.
- The handle path can express a clean bend without becoming a chaotic freehand stroke.
- It gives downstream systems an axial/path reference without allowing unlimited complexity in the first implementation.

The user explicitly allows any angle/shape for now:

- No minimum turn-angle restriction.
- No angle validity restriction.
- Even an acute V shape is allowed by the tool.

Do not add angle policing unless the user asks later.

### Drift Rule Removed

Stage 1 V1 had slice drift logic because it was trying to infer whether a grid-built shape stayed handle-like across a span.

Forge V2 decision:

- The slide/drift rule drops fully.
- Do not replace it with a new alternative drift rule.

Reason:

- The Handle tool directly authors the path.
- The path itself is the intended handle axis.
- If the user authored the handle through the handle tool, the system does not need to infer a clean axis from drifting grid slices.

### Length Rule Remains

Length still matters.

The old Stage 1 values need to be converted into metric Forge V2 values:

- Single-grip minimum: `0.25 m`
- Two-hand threshold: `0.325 m`

This preserves the existing gameplay scale while removing the old grid-first detection method.

Likely first implementation rule:

- A Forge V2 handle is valid as a primary grip if the authored handle spline length is at least `0.25 m`.
- A Forge V2 handle may qualify for two-hand handling if the authored handle spline length is at least `0.325 m`.

Exact downstream two-hand classification can wait until the Forge V2-to-baked-profile bridge is being implemented.

### Data Contract Needed Later

Skill Crafter and combat systems expect weapon geometry information that ultimately comes through baked profile data.

Stage 1 V1 currently resolves things like:

- primary grip contact position
- grip span start/end
- span length
- slide axis
- two-hand eligibility fields
- center-of-mass relation to grip span

Forge V2 should eventually provide equivalent information.

The probable bridge:

- Forge V2 handle body stores semantic role: primary handle/grip.
- It stores selected handle profile id.
- It stores the three handle spline points.
- It stores or can compute metric path length.
- A later bake/bridge resolver converts that into the existing `BakedProfile`-style values expected by downstream systems.

Important:

- Do not try to solve the entire Skill Crafter integration inside the first Handle tool implementation.
- First create the authored handle geometry and semantic metadata cleanly.
- Then bridge into baked grip data.

### Current CSG Profile Shape Limitation

Forge V2 currently uses circular path profiles for the noodle/material spline work.

Handles need non-circular profile support.

Godot CSG path mode can support arbitrary polygon profiles, but the profile must be valid:

- at least 3 points
- non-self-intersecting
- shaped in the expected profile plane

Stage 1 handle masks are grid/row based. They will need an adapter:

- Convert profile mask cells into a metric 2D cross-section.
- Center the profile correctly.
- Scale it using `cell_world_size_meters`.
- Generate an ordered outer polygon suitable for CSG.

Do not fake a handle by using only a circular radius if the selected profile is meant to matter.

### Volume/Cost Implication For Non-Circular Profiles

Current material volume logic is still mostly compatible with capsule/path thinking.

For true handle profiles:

- Material cost should come from swept profile volume, not from circular capsule radius.
- Same-material union should still avoid double-counting overlap.
- Replacement rules should still work as remove-then-add in the affected zone.

This is a later implementation concern, but it must not be forgotten. If the visual CSG uses a handle profile while the accounting resolver still uses a circular capsule approximation, the tool will drift out of project truth.
