
### Current Editor/Active-Selection Seam

The existing implementation does not yet fully obey that separation.

Observed current behavior in code:

- Merely opening the Profiles area does not itself change the active selection.
- Entering the basic 2D builder changes active Forge tool/profile state.
- Loading a saved profile for editing uses the same profile-application path used by Shape selection.
- Confirming Save applies the saved profile to the active authoring state.
- Closing Profiles does not restore the prior tool/profile selection.
- A new draft begins from the circle, but later editor actions can replace the active profile state.

The reason this does not visibly replace circle/sphere deposition today is that basic profile state is still ignored by the actual deposition functions.

This is a dormant correctness problem:

- If basic polygon deposition is connected without first separating editor state from active-use state, saving or editing a profile could silently change future geometry.
- That would violate the user's explicit opt-in rule.

Do not connect the final deposition wire by simply making current `active_profile_id` affect geometry. First establish the correct ownership boundary between an editor draft and an explicitly selected Shape profile.

### Functional Handle, Equip Validity, And Skill Crafter Proof Gap

The Handle/basic distinction is prepared in Forge V2 data, but functional Handle recognition downstream is unproven.

Current state:

- Handle bodies carry a Forge-local tag intended to mean Handle.
- Basic profile bodies would not carry that role.
- This provides the foundation for later primary-grip/hand-position validation.
- No current consumer outside Forge V2 was found that converts this Handle role into Skill Crafter hand placement or baked primary-grip data.
- The June SPS already left that bridge for later.

No current test result proves that the tag is consumed by equip validation, weapon validity, baked grip generation, or Skill Crafter.

Do not claim that the deposited profile "works as a handle" merely because:

- it looks like a handle;
- it was created through the Handles tool;
- its body kind is named `BODY_KIND_HANDLE_PROFILE`;
- its Forge-local role is named `PROFILE_ROLE_HANDLE`;
- the profile extrusion verifier reports `ok=true`.

Those facts prove authored geometry and Forge-local metadata. They do not prove downstream behavior.

A later, separate end-to-end proof must establish the actual chain:

1. Save a weapon containing the authored Handle-profile body.
2. Confirm downstream weapon/baked-profile data receives the required grip information.
3. Confirm equip validity recognizes the weapon and its handle/grip.
4. Confirm the saved weapon can be opened/used in Skill Crafter.
5. Confirm Skill Crafter receives the intended grip/hand-placement meaning.

Until that chain is tested, the accurate statement is:

```text
It draws and deposits a Handle-shaped profile.
It is tagged with Forge's intended Handle role.
Whether it functions as a gameplay handle is unknown.
```

Additional identity caveat:

- Generated Handle bodies currently retain the generic Handle-builder profile id plus a flattened polygon/anchor snapshot.
- They do not retain the stable id of the exact player-saved Handle profile that supplied the data.
- This is not the current 2D-editor task, but it may matter later if downstream systems need the exact authored preset identity rather than only the resulting shape.
