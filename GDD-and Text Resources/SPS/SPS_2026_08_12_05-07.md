## New Current State

### Additive orientation is implemented; subtractive orientation is not

The current new frame is correct for adding material. Remove Material still uses
the additive surface placement, so only the small portion overlapping the target
may be removed. That is not the intended carving behavior.

The corrected intended four-state mapping is:

| Operation | Travel direction | Glyph analogy |
| --- | --- | --- |
| Add | Forward `T` | `d` |
| Add | Reverse `T` | `b` |
| Remove/carve | Forward `T` | `q` |
| Remove/carve | Reverse `T` | `p` |

Therefore:

- reversing `T` mirrors travel-direction handedness: `d <-> b`, `q <-> p`;
- switching Add to Remove reverses only the surface-depth/B-to-C relationship:
  `d <-> q`, `b <-> p`;
- changing both produces `d <-> p`;
- no separately authored negative profile and no hidden double flip are needed.

The intended Remove rule is the opposite camera-side B-to-C hemisphere:

```text
angle ABC at B = 0 through 90 degrees
BA dot BC >= -epsilon
```

`B` stays on the target surface and `T` preserves the user's ordered travel.
The B-to-C depth reflection places the bulk of the same authored profile inside
the target as the cutter, with a small exterior overhang to avoid a zero-thickness
Boolean contact. This is discussed/understood but not implemented.

### Detailing Brush needs a surface geodesic, not only projected samples

The user's C-shaped balloon example is the current thought anchor:

- red and green controls lie on one connected C-shaped surface;
- the intended blue line follows the shortest valid route along the C surface;
- the current yellow connection can take the direct three-dimensional chord
  through empty space;
- if material blocks a chord, current projection can appear to wrap around it,
  but that is not proof of an actual shortest-on-surface solver.

Desired rule:

1. Controls remain exact pass-through points.
2. A span must remain continuously attached to one connected resolved surface.
3. The path is the shortest valid route measured along that surface, including
   conformity around bends and sharp corners.
4. It must not air-jump or silently switch to another disconnected target.
5. If no connected route exists, the span is invalid/red rather than bridged.
6. Dense points, normals, and B-to-C directions are sampled from that resolved
   surface route and remain the generated-body authority.

Same material ID alone is insufficient. Separate iron objects across air remain
separate. Overlapping/contacting passes that actually form one resolved workpiece
need a stable connected-solid/surface identity before geodesic routing can be
reliable.

Still undecided: whether the shortest route may use the entire connected surface,
including a hidden/back-side route, or must stay within a camera-visible/front
region. The C-shaped example suggests full connected-surface distance, but this
requires explicit confirmation on a case where the two choices differ.

## Continuation Checkpoint — One Evolving Workpiece And Geometry Backend

This continuation records a read-only architecture investigation performed
after the preceding shutdown checkpoint. It does not authorize or select an
implementation. No runtime code was changed during this discussion.

The immediate reason for the investigation was repeated CSG Material Stroke
usage eventually seizing the application. Reducing undo depth was considered,
but the investigation showed that undo history is not the main live-geometry
cost.

### User-intended workpiece law

The Forge is intended to produce one evolving physical workpiece. Depositing
or removing material changes that workpiece; a stroke is an authoring action,
not a permanent visible/geometric entity.

Conceptual square-profile example:

```text
first pass                         = 1 x 1.0 x 10
second pass overlapping by 0.5    = 1 x 1.5 x 10
third equivalent pass             = 1 x 2.0 x 10
```

The intended authority is the resolved solid at the current revision, not the
collection of every pass used to create it.

"One workpiece" does not require one literal Godot node, mesh surface, or
collider. Multiple internal render/collision chunks or material surfaces are
acceptable if they remain hidden implementation details under:

```text
one stable workpiece identity
one authoritative geometry/material state
one current accepted revision
one bounded compilation state
one live drawing preview
zero permanent stroke CSG operands
```

### What current Forge V2 actually does

- Every completed stroke remains a separate `ForgeV2MaterialBody`.
- CSG Material Stroke release automatically commits that body as a layer.
- Commit adds metadata/accounting authority; it does not merge the new body
  into an older body or replace the old geometry with one consolidated mesh.
- Same-material bodies whose conservative AABBs intersect are grouped into one
  static CSG zone. The zone looks and collides like one Boolean result, but
  every source stroke remains a separate child CSG operand.
- For ordinary same-material addition, the visible seam/bridge is not another
  stored connector body. It is Boolean result geometry, source sweep geometry,
  triangulation/tolerance, and/or shading.
- Adding one connected stroke changes the zone membership/key. The previous
  zone is discarded and the complete growing zone is reconstructed.
- Pure same-material operand quantity grows approximately linearly, not as an
  uncontrolled power of N. Cumulative authoring cost still grows much faster
  because release N reprocesses operands 1 through N.
- VOID, replacement-material, Empty Only, and protected-Handle clipping can
  duplicate clipping operands beneath multiple body combiners and produce a
  worse CSG graph.
- Zone connectivity is currently broad-phase AABB intersection, not exact
  topological contact. Non-touching geometry with overlapping bounds may enter
  the same expensive tree, and one long body may join several zones.
- One concave collision result is created per zone, but that whole collision
  result is regenerated when the zone is rebuilt.

Current Forge V2 therefore has:

```text
one combined-looking visual result
one approximate consolidated material-accounting map
but a permanent per-stroke geometry/history stack
```

There is no current runtime baked workpiece authority. Layer commit is
`ledger_only`; baked mesh and collision references are unused placeholders;
Forge V2 WIP saving preserves the full AuthoringState and leaves the old baked
profile snapshot null.

Undo/redo currently toggles layer bodies active/inactive. Reducing the undo
limit alone would not consolidate active bodies and therefore would not solve
the live CSG scaling problem. Once rendering is separated from history,
reducing undo may save history memory but should not affect render cost.

### Existing reusable authority

`ForgeV2MaterialVolumeResolver` already implements much of the desired ordered
composition law in one cell-to-material result:

- same-material overlap is counted once;
- Replace Existing changes material ownership;
- Empty Space Only preserves occupied cells;
- VOID removes ordinary occupied cells;
- Handles replace/cannibalize prior material and protect their cells from
  later ordinary addition/removal;
- incremental append-only accounting can reuse the previous resolved map.

This is an important semantic foundation, but it is not suitable as final
geometry as written:

- it is transient and not a saved workpiece;
- it has no mesh, collision, normals, UVs, or surface connectivity;
- it uses center-sampled `Dictionary<Vector3i, ...>` storage;
- its global spatial resolution is 0.0125–0.025 m;
- it cannot preserve 0.001 m fillets, 0.0005 m contact clearance, thin walls,
  small gaps, or exact custom-profile corners.

The 0.0125 m material-accounting reference volume must be separated from future
geometry resolution. Making geometry finer must not silently change material
economy or quantities.

### Godot 4.7 facts relevant to a replacement

- Godot 4.7 built-in CSG already uses bundled Manifold 3.3.2 for Boolean work.
  The problem is not simply an obsolete Boolean algorithm; it is also the
  permanent growing tree and compilation lifecycle.
- Built-in CSG updates are deferred SceneTree/node work. Boolean resolution,
  output mesh generation, and enabled collision refresh occur through that
  path.
- Godot compiles its bundled Manifold without its parallel/TBB mode, so the
  built-in CSG calculation is sequential internally.
- `bake_static_mesh()` returns the CSG root's currently resolved `ArrayMesh`.
  It requires the deferred CSG update to complete first; it is not a separate
  free/asynchronous Boolean operation.
- A baked `ArrayMesh` can be used as the next `CSGMesh3D` input if it remains a
  valid closed manifold.
- Refeeding through `CSGMesh3D` does not retain arbitrary semantic attributes.
  Handle identity, volumetric material ownership, and provenance require a
  parallel authority.
- SceneTree CSG cannot safely become a WorkerThreadPool job. Background work
  must operate on immutable numeric data and publish nodes/resources on the
  main thread.
- Godot's embedded Manifold API is not exposed to GDScript/GDExtension. A true
  background exact-Boolean backend would need to vendor/link Manifold inside a
  C++ GDExtension, or expose it through a custom engine module.

### Backend-neutral target

Do not bind Forge tools directly to the next geometry implementation. Preserve
existing tool work by introducing a conceptual boundary:

```text
Drawing Tool
    -> immutable WorkpieceCommand
    -> authoritative ForgeV2WorkpieceState revision
    -> interchangeable GeometryBackend
    -> derived render mesh/collision
```

A command needs, as applicable:

- resolved path/profile geometry;
- Add or Remove operation;
- material `.tres` identity;
- placement policy;
- Handle semantic role/region;
- explicit B-C, surface-normal, and T orientation data;
- hard or future soft seam/blend radius.

A workpiece snapshot needs:

- stable workpiece ID;
- revision and compiler/schema version;
- canonical geometry authority;
- material and protected-Handle authority;
- exact authored Handle records for future grip/Skill Crafter use;
- material totals;
- derived render/collision references or caches;
- checkpoint revision and bounded undo/redo state.

The useful compiler concept is:

```text
compile(base_snapshot, ordered_commands) -> new_snapshot
```

This boundary permits a rolling Godot CSG proof, a native Manifold worker, and
a sparse SDF/volume backend without rewriting the authoring tools each time.

### Candidate A — rolling built-in CSG bake

```text
steady state:       one baked base
compile state:      baked base + current operation
accepted state:     one newly baked base
```

If current operand count is the dominant cost and repeated baked geometry
remains valid/manageable, this can provide a large improvement with the tools
already available.

If processing time follows the growing baked mesh's triangle/intersection
complexity, operand count becomes constant but milliseconds do not.

If repeated bake/refeed produces slivers, topology failures, profile drift, or
unacceptable main-thread stalls, stop this route rather than forcing it.

A front visible mesh plus hidden staging CSG permits a clean visual swap, but
the built-in Boolean still blocks the frame that executes it. Double buffering
changes when the hitch occurs, not whether it occurs.

This is the least expensive and most informative first proof. It is not yet
assumed to be the final backend.

### Candidate B — native Manifold geometry compiler

A C++ GDExtension can vendor an upstream Manifold build and operate on immutable
mesh arrays off the SceneTree:

```text
accepted mesh arrays + new command
             -> worker Manifold Boolean
             -> output arrays/material mapping
             -> main-thread atomic mesh/collision publication
```

If rolling exact mesh geometry is correct but Godot's main-thread release hitch
is the remaining failure, this is a credible escalation without an engine fork.

It also requires native builds for every target platform, revisioned job queues,
stale-result rejection, material/semantic mapping, and long-term native-code
maintenance.

Moving a whole-growing-mesh Boolean to a worker does not by itself solve total
work. If compile duration still rises with complete workpiece complexity, the
background queue eventually falls behind the user.

Exact mesh Boolean naturally provides hard union/subtraction. Adjustable soft
seam/vacuum-bag behavior remains a separate geometry operation.

Do not attempt to write a robust triangle-Boolean kernel from scratch. The
original project work should be the Forge-specific workpiece lifecycle,
semantics, spatial updating, and tool integration—not reinvention of a mature
computational-geometry library.

### Candidate C — sparse material-aware SDF/volume workpiece

A signed-distance field stores distance to the surface:

```text
negative = inside
zero     = surface
positive = outside
```

Core operations become:

```text
hard addition:   result = min(workpiece, tool)
subtraction:     result = max(workpiece, -tool)
soft addition:   result = smooth_min(workpiece, tool, blend_radius)
```

This is the strongest conceptual match for indefinite deposition/removal and
the future adjustable seam/vacuum-bag control. A zero blend radius is hard
union; increasing a meter-based radius generates progressively fuller/rounder
joining.

Initially permit soft joining only for matching materials. Different-material
bridge volume needs an explicit material-ownership rule before it is valid.

The canonical field needs parallel channels such as:

```text
geometry distance/occupancy
material ID
semantic flags
Handle region ID
```

Exact Handle authoring records remain separately persisted. Grip validity must
not be inferred only from the visible shell because detailing may visually
engulf a still-valid Handle region.

The workpiece must be sparse and chunked. A dense one-metre cube at fine
resolution is not viable. Approximate ideal packed memory at eight bytes per
sample is:

```text
2.0 mm dense 1 m cube  ~= 1 GB
1.0 mm dense 1 m cube  ~= 8 GB
0.5 mm dense 1 m cube  ~= 64 GB
```

Weapon-local sparse allocation is much smaller, but 0.5 mm can still be costly.
Fixed packed chunks (for example 32 cubed samples) and allocation only around
occupied/narrow-band regions are required. GDScript dictionaries per fine voxel
are not appropriate final storage.

If one operation touches three chunks, only those chunks plus their boundary
halo should update/remesh. Then comparable local edits should cost roughly the
same at stroke 10 and stroke 10,000.

Meshing candidates:

- greedy voxel mesh: inexpensive but too block-like for final profile work;
- Marching Cubes: useful architecture proof, but rounds deliberate corners;
- Surface Nets: fewer vertices but still weak for hard profile features;
- Dual Contouring: strongest sharp-feature candidate, but harder to make
  watertight and crack-free across chunks.

The live resolution and final mesher must be selected by measurement against
the asymmetric profile, square corners, 0.001 m fillets, 0.0005 m clearances,
thin gaps, VOID, and repeated overlap. Do not choose a resolution by intuition
alone.

### Candidate D — hybrid

A hybrid may use one field/material authority for semantics, targeting, and
local edits while an exact native mesh compiler produces a presentation/final
surface.

If the two representations disagree visibly, the user receives a misleading
preview/final result. Therefore any hybrid must prove identical placement law,
bounded error, and safe surface targeting. It is not automatically safer merely
because it combines both approaches.

### Background compilation law

Background work is useful only after computation is bounded or spatially local.

The desired bounded state is:

```text
one accepted front revision
one coalesced pending/dirty revision
one lightweight live preview
```

If a newer edit arrives while a compile is running:

1. increment the workpiece/chunk revision;
2. merge overlapping dirty regions rather than queueing infinite jobs;
3. discard any completed result whose revision is stale;
4. atomically publish only current mesh/collision output.

Do not silently target stale collision. Either raycast the authoritative field,
freeze the target revision for the duration of an active stroke, or temporarily
make a dirty region non-targetable until its collision catches up.

Saving must persist the canonical accepted workpiece revision, not whichever
derived mesh happened to finish compiling most recently.

### Undo/checkpoint law

An inverse Boolean is not a general undo. Once `A union B` is baked, the internal
faces needed to reconstruct A may no longer exist.

For a field backend, recent commands should retain affected-region deltas:

```text
before geometry/material/semantic values
after geometry/material/semantic values
```

For an exact-mesh backend, undo requires bounded prior snapshots or checkpoint
plus command replay.

History should be bounded by both action count and memory size because one long
stroke may change more data than many small strokes.

Conceptual form:

```text
checkpoint revision 200
recent reversible commands/deltas 201..232
current revision 232
```
