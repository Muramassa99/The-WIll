This is the stop/resume handoff for the Forge V2 Add-material latency work. It
records what was measured, what is genuinely implemented, and the blockers
found before the intended `checkpoint + last five + protected handle` system
could be accepted. No commit, push, or destructive cleanup is implied.

## User Goal - Authoritative

The product goal is flow-state material deposition, not a faster isolated
Boolean benchmark.

- Stroke 1 through stroke 5,000 or 20,000 should cost approximately the same.
- Max/tail hangs matter more than the minimum or mean. A flatter distribution
  is preferable even if the minimum becomes slightly slower.
- Keep the current smooth, profile-drawn surface and targeting behavior.
- Measure both SPM and release-to-next-targetable latency.
- The chosen Add history law is one accumulated checkpoint plus five undoable
  tail strokes.
- At total stroke `N > 5`, checkpoint represents `N - 5` and the tail contains
  the newest five strokes. Exactly five undo steps remain available.
- The protected/default Handle stays separate, giving the intended logical
  `checkpoint + 5 + Handle = 7` bounded-body situation.
- Remove/VOID follows after Add is manually accepted. Approximately three
  times Add latency is acceptable for Remove if its result is correct.

## Why The Direction Changed

The earlier regional publication-atlas experiment proved a local Manifold
Boolean can be about 3-4 ms, but its Python conditioning/publication proof took
seconds per edit. That work established useful locality and correctness laws;
it did not produce a usable release path and must not be revived wholesale.

The rolling five-history Godot CSG experiment also bounded operand count but
kept Booleaning one ever-growing baked mesh. At operation 5,000 it measured
about 850 ms p95 and retained a near-linear per-operation growth slope. It is
not the scaling solution.

The useful finding is narrower: Godot 4.7 already uses Manifold internally,
but repacks the complete CSG tree and republishes the complete mesh/collision.
Calling the same Manifold kernel directly and retaining native state removes
that tree-history overhead. The remaining app-level history, metadata, UI,
publication, and collision work must also be bounded.

## Blockers - Do Not Run The 1,000 Acceptance Test Yet

1. **Protected Handle blocks the native bounded lane.** The presenter currently
   rejects native bounded operation whenever protected geometry exists. At
   stroke six, promotion is rejected, six source layers are restored, and
   bounded history is suspended. Therefore the requested `1 + 5 + Handle`
   model is not currently reachable.
2. **Dirty checkpoint lifecycle loss.** Controller rebind, state replacement,
   and presenter clear paths can clear the native backend after clearing the
   export provider. If S0 is dirty, folded geometry can be lost. Every
   non-destructive reset must materialize/validate S0 first; failure must retain
   the old backend/publication.
3. **Promotion occupancy is not fully transactional.** The resolver currently
   mutates checkpoint dictionaries by reference before checkpoint advance is
   committed. Replace this with a touched-cell delta/journal and atomic apply,
   without duplicating the whole growing occupancy map.
4. **Unsupported/different-material Add after S0 is unsafe.** The existing
   fallback validates every tail body as the same-material native lane. A
   different-material Add may commit in state but fail to publish. Until a
   chronological checkpoint-base fallback exists, reject such a commit before
   state mutation rather than accepting invisible state.
5. **Surface identity needs checkpoint identity.** Include checkpoint ID and
   revision/geometry identity plus tail/protected signatures, not only the
   checkpoint operation count.
6. **The newly added app integration has only parse validation.** There is no
   accepted 6-, 20-, 100-, or 1,000-stroke app-level bounded result yet.

## Recommended Protected-Handle Seam

The smallest promising exact design to verify is:

1. Keep the native history backend tracking only the aggregate Add solid and
   continue native promotion/undo/redo even when one protected Handle exists.
2. Use the already exported current native aggregate as one `CSGMesh3D`
   operand; do not export S0 on promotion.
3. Publish a constant-size composition equivalent to current protected policy:
   `(aggregate_add - handle) union handle`.
4. This preserves separate Handle material and prevents later Add from
   replacing Handle cells while keeping the tree bounded. Reuse the current
   double-buffered publication/readiness guard.
5. Initially support exactly the normal single protected Handle. Treat shield
   or bow platform seeds and multiple protected handles as explicit fallback
   cases until separately proven.

This is a continuation design, not implemented or measured at this stop.
