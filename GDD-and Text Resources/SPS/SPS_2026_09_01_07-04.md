Current implementation:

### 2. Startup and Reset now request one real active grip solve

Touched:

- `runtime/combat/combat_animation_station_ui.gd`
- `runtime/combat/combat_animation_station_preview_presenter.gd`

Cause found:

- skill entry supplied a grip-related reason but the authored pose branch allowed
  an exact surface solve only when a live drag override existed;
- Reset explicitly cleared grip targets and committed seat/grasp caches, then
  refreshed without an exact-grip reason;
- viewport resize could perform a full pose refresh and overwrite the intended
  startup/Reset result.

Current implementation:

- `active_grip_state_requested` is a one-refresh command that authorizes the exact
  Handle seat and digit solve;
- selecting an armed skill/draft, selecting/removing a motion node whose authored
  relationship may differ, changing primary hand, changing grip style, and Reset
  route through this deliberate exact boundary;
- Reset still restores the macro/node baseline first, then applies the currently
  active normal/reverse grip relationship;
- viewport resize refreshes selection/size visuals only.

### 3. Ordinary weapon/body editing reuses the committed contact packet

Touched:

- `runtime/player/player_rig_finger_grip_presenter.gd`
- `runtime/player/player_humanoid_rig.gd`
- `runtime/combat/combat_animation_station_preview_presenter.gd`
- `runtime/combat/combat_animation_station_ui.gd`

Cause found:

- the old lightweight path called the exact-seat resolver with exact work disabled;
- that returned a cached seat only when the complete live quantized context key
  happened to match;
- ordinary Tip/Pommel/roll/body movement changes live transforms, so the key could
  miss and contact appeared intermittently lost;
- the previous `relationship_contact_packet_reused` marker was mostly diagnostic,
  not proof that the packet had actually been replayed.

Current implementation:

- the finger-grip presenter exposes the last valid committed weapon-local surface
  seat without requiring the current transform-derived context key to match;
- the humanoid rig exposes that packet to the Skill Crafter presenter;
- ordinary manipulation starts from the fresh authored weapon transform, reapplies
  the committed weapon-local dominant seat, recomposes grip guides/support anchor,
  runs one cheap macro frame, then restores the committed dominant 15-digit packet
  and the support packet when active;
- this reuse path is active both during held 3D manipulation and after release;
- direct numeric Tip, Pommel, orientation, weapon-roll, body-support, upper-arm,
  Bezier-handle, and free-hand-proxy edits use the same continuity path;
- changing Handle position, primary/support grip seat, grip style, two-hand state,
  or primary hand remains a true relationship change and performs one exact solve;
- acceleration/deceleration UI edits preserve the existing contact relationship;
- continuity-marker changes are pose-neutral.

This follows the user's table/cup rule: moving the weapon/body macro frame does not
by itself change where the hand is attached to the Handle.

### 4. Manual Save exact-pose baking is incremental

Touched:

- `runtime/combat/combat_animation_station_preview_presenter.gd`
- `runtime/combat/combat_animation_station_ui.gd`

Cause found:

- a representative 145-frame upper-body/runtime replay bake took about `31.44 s`;
- all frames were solved synchronously inside one UI frame;
- pending collision publication could add roughly another `2.03 s`, but that queue
  was preview metadata and was not serialized Save authority.

Current implementation:

- exact runtime-pose baking now has `begin`, one-or-more-frame `advance`, and
  `finalize` stages;
- the original synchronous wrapper remains for existing tools and compatibility;
- manual Save advances one exact frame, yields one process frame, updates progress,
  and continues until the same pose/replay track is complete;
- pending preview-only collision-path work is canceled before Save because it is
  neither serialized data nor a Save gate;
- after persistence, the editor pose is restored and the active grip is solved once.

Future collision hitboxes, damage calculations, and WIP-derived handling/
acceleration products are not current Save prerequisites. Their absence did not
cause the observed Save hang. They remain future integrations and must not be
silently invented as blockers in this slice.

### 5. Focused incremental-bake verifier added

New untracked verifier:

- `tools/verify_runtime_pose_track_incremental_equivalence.gd`

It builds an in-memory synthetic WIP, never loads or writes the live WIP library,
and compares the synchronous wrapper against `begin -> one-frame advance ->
finalize` across all finalized pose/replay-track fields and result metrics.
