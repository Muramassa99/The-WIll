## Reading and maintaining this list

- **Planned:** requested future outcome; not permission to begin it now.
- **Decide:** intent exists, but a core behavior or choice still needs agreement.
- **Verify:** implementation/evidence exists, but the stated scenario lacks current acceptance. It is not a confirmed bug.
- **Historical review:** older design intent worth retaining; current implementation and desirability must be checked before starting.
- **Parked:** deliberately deferred or optional. Do not pull it into an active fix automatically.
- Checked entries record completed scope, with qualifications; most are grouped near the end. They do not claim every possible variant is correct.

Before implementing an entry, read its sources, inspect its actual current owner and choose a bounded acceptance test. Add new details to the existing ID when scope matches. Mark completion with dated evidence; do not delete inconvenient verification gaps or create a second entry for the same outcome. Exact tuning values in old design documents remain historical unless reaffirmed below.

### Topic expansion rules — agreed 2026-10-26

- Expand and preserve information for later implementation. Rewriting the documentation for phone use or data portability is not a requirement of this pass.
- Create a dated, topic-specific Markdown brief for each topic discussed. Keep the existing checklist IDs and link them to that brief; several related IDs may share one coherent brief.
- Gather the related material from original specifications, task notes, SPS and relevant current code. Consolidate the useful requirements in the brief, with source links, so the future implementer has the context rather than only a reading list.
- Today's explicit decisions override contradictory older decisions on that topic. State what was superseded and why; preserve original historical files. Carry forward older complementary information that today's discussion did not replace.
- Keep approved requirements, current code observations, historical verification, optional older ideas and unresolved decisions distinguishable. Missing core rules stay `NEEDS_DECISION`; research does not authorize inventing them.
- Each brief should contain the intended outcome, relevant existing behavior, required changes, dependencies, boundaries and completion checks. It must be usable later when the user says "we will do that today", with unresolved details addressed during that implementation discussion.
- The expansion pass authorizes documentation and investigation, not blanket implementation of the described game changes. SC-01, UI-02's duration controls and SC-07 were subsequently explicitly authorized and implemented. Other topics remain documentation scope; runtime checks must respect the one-run-at-a-time rule.
